# AIRENOS IDENTITY F2.4 — PROVIDER APPLY PACKET

Date: 2026-09-04
Governance: RULE-DOC-20 / RULE-DOC-21
Classification: STATIC PROVIDER APPLY PACKET / NON-PRODUCTION / NO LIVE APPLY AUTHORIZED BY THIS DOCUMENT

## 1. Purpose

F2.4 freezes the provider-apply packet that must be satisfied before any real non-production Identity staging apply may be considered. This checkpoint is documentation and deployment-contract governance only. It does not create provider resources, does not execute a billable action, does not create a live signing key, and does not authorize production.

F2.4 descends append-only from F2.3 and preserves every certified protected boundary.

## 2. Canonical infrastructure direction

- OVHcloud Public Cloud, Milan `EU-SOUTH-MIL`, remains the canonical infrastructure target for AIRenOS Identity staging.
- The intended Milan topology remains three availability zones: `eu-south-mil-a`, `eu-south-mil-b`, and `eu-south-mil-c`.
- Render, where used by the F2.3 contract, remains a temporary non-production proof-host / execution adapter only.
- Render is infrastructure only. It is never Identity, ProductAccess, Entitlement, licensing, subscription, billing, tenant, or business authority.
- Existing RISTOAIREN / AIRen Booking Render resources are outside this Identity scope and must not be reused as Identity authority or state.

## 3. Dedicated Identity topology

Any future provider apply must preserve a dedicated Identity boundary. At minimum:

1. Session Authority runtime is isolated from product runtimes.
2. Identity persistence is dedicated to Identity and must not reuse the AIRen Booking database.
3. Keycloak is a separately governed dependency and is not the AIRenOS Session signing authority.
4. Foundation remains the platform authority that consumes the Session Authority public verification material and governed session output.
5. Base44 remains a replaceable Experience Layer and may not become Identity or ProductAccess authority.

No provider convenience may collapse these boundaries.

## 4. Secret and signing-key boundary

Secrets MUST remain outside Git source, Google Drive governance documents, Base44 source, chat transcripts, CI logs, any unprotected Terraform state, and any user-visible evidence capture. If infrastructure state contains provider-generated sensitive material, that state must remain inside an explicitly protected provider/state boundary and must never be copied into governance evidence.

The Session Authority private Ed25519 signing key:

- must not be generated by this F2.4 registration;
- must not be pasted into chat;
- must not be committed to Git;
- must not be stored in Google Drive governance documents;
- must be generated only at the later explicitly authorized live staging step, inside the approved provider/secret boundary;
- must remain exclusive to Session Authority.

Foundation receives only public verification material, represented by the governed public JWK keyring (for example through `AUTH_SESSION_PUBLIC_KEYS_JSON`). Foundation must never receive the Session Authority private signing key.

The same boundary applies to database passwords, Keycloak client secrets, provider access tokens, API secrets, and equivalent credentials.

## 5. Keycloak boundary

Keycloak may provide OIDC authentication and the Authorization Code + PKCE S256 path established by F2.3, but it must not become the AIRenOS Session signing authority. Any real staging Keycloak configuration is a later live write and requires its own direct evidence/read-back.

No production realm, production client, or production secret is authorized here.

## 6. Provider apply prerequisites

A future staging apply must fail closed unless the applicable provider evidence is independently read back and reconciled. For the canonical OVH path this includes, as applicable:

- existing governed Public Cloud project;
- provider project/service identifier;
- `EU-SOUTH-MIL` status and availability;
- `region-3-az` topology;
- exact Milan availability zones;
- required compute flavor / quota readiness;
- PostgreSQL 17 capability;
- expected database plan and flavor capability;
- schema/migration execution readiness and a least-privilege Identity runtime-role plan;
- least-privilege provider credential path bound through an approved secret channel;
- no ambiguity between legacy and OAuth2 authentication paths.

The existing OVH preflight remains read-only/data-source-only and does not itself authorize apply.

## 7. Ordered non-production apply sequence

If and only if a later gate explicitly authorizes a real staging apply, the following governance preflight must pass before provider mutation begins:

- fresh RULE-DOC-21 reconciliation across GitHub and Google Drive;
- verification of all protected product/platform boundaries and PR #4;
- provider project, region, quota, and capability evidence;
- cost-impact review for every billable resource to be created.

Only after that preflight passes, the provider provisioning and proof order is fixed as follows:

1. create a dedicated Identity PostgreSQL boundary;
2. apply the governed Identity schema/migrations and establish the least-privilege runtime role;
3. deploy/configure dedicated Keycloak staging;
4. create/configure the staging OIDC client for Authorization Code + PKCE S256;
5. deploy the F2.3 Session Authority runtime on the approved temporary Render non-production proof host, without reusing Booking state;
6. bootstrap the first real staging Ed25519 private signing key only inside the approved provider/secret boundary;
7. perform direct public JWK read-back without disclosing private material;
8. bind only the public JWK keyring to Foundation;
9. perform an independent thumbprint/read-back comparison across the Session Authority public JWK and the Foundation verification material;
10. prove a real OIDC Authorization Code + PKCE S256 flow against staging Keycloak;
11. prove issuance and verification of a real AIRenOS Session;
12. execute the RA-01 ProductAccess / effective entitlement / handoff E2E only after the real AIRenOS Session proof is valid;
13. govern and attach the Experience Layer separately only after the authority path is proven.

A failure or mismatch at any step stops the sequence. Partial evidence does not promote a later gate. Remote read-back and cross-source reconciliation remain mandatory after every governed write.

## 8. Rollback and containment

Any future apply plan must have a rollback/containment path before execution. At minimum:

- runtime failure must not alter protected product branches;
- failed Identity staging resources must not be promoted to production;
- secrets must remain revocable without rewriting Git history;
- signing-key rotation must remain overlap-first under the F2.1 lifecycle contract;
- rollback must not require weakening R3-I, RA-01, RISTOAIREN, Booking, Pay, Kairos, or AIRenOS platform boundaries;
- resource teardown must be explicit and separately evidenced where it can destroy state;
- no rollback or teardown may delete, mutate, repurpose, or attach Identity authority to the existing RISTOAIREN / AIRen Booking Render services or databases.

No destructive action is authorized by F2.4.

## 9. Cost-control boundary

Before any billable provider action, the operator must be able to identify the resources to be created, their staging-only purpose, and the expected billing surface. F2.4 does not authorize a purchase, subscription, charge, paid database, paid compute instance, load balancer, managed secret service, or any equivalent billable resource.

Provider account/payment readiness does not equal apply authorization.

## 10. Protected non-claims

At F2.4 registration time the following remain NOT established by this document:

- live OVH provider apply;
- live Render Identity service creation by F2.4;
- new billable resources;
- dedicated live Identity database;
- live Keycloak staging write;
- Secret Manager / KMS effective binding;
- real staging Ed25519 private signing key;
- live Session Authority public JWK keyring;
- Session Authority staging deployment;
- Foundation staging public-keyring binding;
- `session.airenos.com` DNS/TLS activation;
- real AIRenOS browser session issuance;
- RA-01 real-session ProductAccess / handoff / E2E;
- Base44 Experience attachment;
- production enablement.
