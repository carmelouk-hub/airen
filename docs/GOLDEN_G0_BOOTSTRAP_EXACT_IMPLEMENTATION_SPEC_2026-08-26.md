## 2. Environment topology

Governance environment class: `DEMO_CERTIFICATION`.
Database Booking `environment_class`: existing schema value `DEMO`.

Trusted base domain for tests: `golden.ristoairen.test`.
Primary trusted hostname: `golden-g0.golden.ristoairen.test`.
Secondary Location hostname: `golden-g0-l2.example.test`, registered and activated as a TenantDomain bound to G02.

No purchased or production domain is used by G0.

Tenant logical identity:
- slug: `golden-g0`
- name: `Golden Restaurant G0`
- locale: `it-IT`
- timezone: `Europe/Rome`
- currency: `EUR`

Locations:
- G01: slug `main`, name `Golden Main`, primary=true
- G02: slug `annex`, name `Golden Annex`, primary=false

Physical UUIDs are Foundation-generated by governed provisioning and are frozen into the runtime fixture/evidence manifest after first bootstrap. Runtime must never bypass canonical Tenant/Location commands merely to force predetermined UUIDs.

## 3. Provisioning path

G01 Tenant + primary Location must be created through canonical `provisionTenant` under a platform security context with `platform.tenants.provision`.

G02 must be created through canonical `createLocation`, which requires `tenant.locations.manage`, `tenant.multi_location` and trusted Tenant scope.

The G02 hostname must use the existing TenantDomain lifecycle: register -> verification start -> trusted test verification evidence -> activate, bound to G02.

Direct SQL insertion into `platform.tenants`, `platform.locations` or `platform.tenant_domains` is forbidden for G0 runtime implementation.

## 4. Actor matrix

G0 minimum actors:

1. `golden_manager`
   - canonical role: `manager`
   - active TenantMembership
   - active LocationMembership on G01 and G02
   - required Booking permissions: `booking.read`, `booking.create`, `booking.update`, `booking.status.update`

2. `golden_responsabile`
   - canonical role: `responsabile`
   - active TenantMembership
   - active LocationMembership on G01
   - required Booking permissions: `booking.read`, `booking.status.update`
   - must not receive `booking.create` or `booking.update`

3. `golden_bootstrap_platform_actor`
   - platform-only bootstrap authority
   - used only for governed provisioning/domain lifecycle
   - cannot become an operational Restaurant actor

4. service actor `golden-g0-experience`
   - EdDSA service assertion, audience `airenos-foundation`
   - no Tenant/Location authority in the token

Authentication identities use provider-neutral sessions. Client/provider identity evidence is never final authorization authority.

## 5. Booking persistence environment correction

Current Booking repository hardcodes `TEST_TEMPORARY`. G0 runtime implementation must replace that hardcoding with a server-owned constructor/config value matching the existing database enum:

`TEST_TEMPORARY | DEMO | SANDBOX | PRODUCTION`

For G0 it is fixed to `DEMO`.

The value must never come from Booking request DTOs, query parameters, headers or Base44/client state.

T20 constructors/tests must remain fixed to `TEST_TEMPORARY` and continue to pass unchanged semantically.

No schema enum expansion is required for G0.

## 6. G0 bounded test ingress

Use the existing private Booking dispatcher and security-context resolver; do not publish `apps/api/src/server.ts` in G0.

Required ingress proofs:
- trusted hostname `golden-g0.golden.ristoairen.test` resolves Golden Tenant + G01;
- active custom TenantDomain `golden-g0-l2.example.test` resolves same Tenant + G02;
- unknown hostname fails closed;
- bearer authentication required;
- EdDSA service assertion required;
- SecurityContext derives Tenant/Location from route + membership, never client DTO fields;
- G01 request cannot read/write G02 Booking and vice versa;
- manager can create/query Booking;
- responsabile can read/status-transition but cannot create/generic-update;
- correlation id appears in response/audit/outbox evidence.

G0 does not claim public guest Booking and therefore does not mark DOC-015 `GR-T02` fully PASS.

## 7. Fixture dataset

Permanent topology:
- one Golden Tenant;
- two Golden Locations;
- two operational identities + memberships;

- one active custom test TenantDomain for G02.

Scenario data is resettable and must include at least:
- one future Booking in G01;
- one future Booking in G02;
- one status-transition scenario;
- one idempotent replay scenario;
- one denied cross-location scenario;
- one denied unauthenticated scenario;
- one denied responsabile create/update scenario.

All scenario Bookings use `environment_class='DEMO'`.

## 8. Reset algorithm

Golden reset is Foundation-owned and fail-closed.

Before deletion it must resolve and assert the exact Golden Tenant slug `golden-g0` and the physical Tenant UUID captured in the Golden fixture manifest.

Deletion predicates must use the exact Golden Tenant UUID; no prefix/wildcard Tenant deletion is allowed.

Reset removes scenario state only:
1. Golden Booking outbox rows;
2. Golden Booking audit rows;
3. Golden Booking idempotency rows;
4. Golden `risto_bookings` rows with `environment_class='DEMO'`.

Reset preserves:
- Golden Tenant;
- G01/G02 Locations;
- identities and memberships;
- Golden TenantDomain;
- canonical permissions/role grants;
- all T20 fixtures;
- all production/Corte data.

After reset assert zero Golden Booking, idempotency, Booking outbox and Booking audit scenario residue.

## 9. Evidence schema

Every G0 run records:
- run_id;
- branch/commit/tree;
- environment class;
- Golden Tenant UUID + slug;
- G01/G02 UUID + slugs;
- hostname -> Tenant/Location resolution evidence;
- actor identity/membership references;
- scenario IDs;
- expected/observed;
- correlation ids;
- audit/outbox references;
- reset counts;
- protected-scope assertions;
- final verdict.

No secret, bearer token, service private key or raw sensitive customer data may enter evidence.
